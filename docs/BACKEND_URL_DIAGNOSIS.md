# 部署 /exec 與 GS 自動顯示網址不一致：調查及處理紀錄（深資 vsbadge）

調查及修正日期：2026-10-24；深資 GS 版本：v9.2。本文件按幼童軍 cubsbadge 的同系交接指示及同名調查記錄，核實深資自身程式後寫成。

> **最終決定：接入資料只提供 API Key；旅團編號在 ADMIN FORM 填寫，不顯示未能確認的部署 URL。**
> 不新增要求用戶貼網址／設定 BACKEND 的步驟。先前同系曾建議的自動核實／手動 URL 設定方案一律沒有採用。

## 1. 原因

**原本程式把 `ScriptApp.getService().getUrl()` 當成領袖剛剛選定的部署 URL，但兩者不是同一個資料來源。**

- Google「部署 → 管理部署」視窗顯示的是該視窗中選定的部署入口。
- Sheet 選單及初始化執行的是一般函式；程式沒有接收那個部署的 ID，也沒有讀取部署視窗的選擇。
- 同一個 Script 專案可以有多個部署。不能假設 `getUrl()` 就是剛新增／剛選定的那一個。
- 原本初始化彈窗、初始化回傳值及選單各有取值路徑，與舊快取未必相同，所以可能出現第二、第三條網址。

因此，即使領袖「剛部署完成，立即查看」，程式仍未能保證兩條網址相同；不能歸咎於領袖未等夠時間，也不能要求領袖辨認內部部署 ID。

沒有取得實際旅團的部署清單及執行紀錄，所以尚不能判定另一個 ID 在 Google 內部屬於舊部署、另一個部署還是異常回傳。這不影響停止顯示不可靠 URL 的處理決定。

## 2. 深資原有寫法（修正前）

修正前 `apps-script/Code.gs` 有兩處面向領袖的自動取值：

- `initializeSheets()` 結尾以 `ScriptApp.getService().getUrl()` 組成 `scriptUrl`，同時放進完成彈窗及執行回傳物件；
- `menuShowLinkCredentials()`（舊選單「顯示 BACKEND／APIKEY」）直接讀同一方法，當作 BACKEND 顯示。

同系調查亦確認童軍、樂行版本曾有相同寫法；各支部按交接指示在自己的 repository 分別修正，任何一個合併都不代表其他 repository 或各旅團 Google 部署已更新。

檔案內另有一個內部驗票流程使用同一取值作連線用途。這是登入協定的一部分，**本次沒有改寫**：只處理接入顯示及指南，不藉今次修正宣稱所有 URL 身分比對風險已消除。

## 3. 撤回不可靠說法（不得再用來指示用戶）

- 以部署 ID 長度判別部署類型或有效性：長度不能證明任何事。
- 在 `doGet`／`doPost` 內叫 `getUrl()` 就必然得到實際請求入口：不能依賴這個假設。
- 開一次 `/exec` 後就「記啱」網址：若來源錯，自動寫入的快取也會錯；其他請求亦可能覆寫快取。
- 自報 URL 的自我查詢等於獨立核實：它仍讀回同一來源，屬循環確認。
- 存在 URL 快取或顯示「已核實」就可收貨：格式合格不能證明是領袖選定的部署。

深資由始至終沒有在普通請求加入自動記錄網址或自報查詢路由；回歸測試會守住普通請求不改寫任何 URL 快取、亦不存在此類入口。

## 4. 深資實際處理（GS v9.2）

| 位置 | 處理 |
|---|---|
| `initializeSheets()` 彈窗 | 顯示初始化結果、原有首次登入提示及現有 API Key，不提示輸入旅團編號、不顯示自動部署 URL |
| `initializeSheets()` 執行回傳值 | 移除 `scriptUrl`，避免在執行結果出現另一條錯網址 |
| `showApiKey()`／`showVercelEnv()`／`vercelEnvLines()` | 只提供同一隻 `API Key = ...`，不依賴旅團編號、不提供 BACKEND 值 |
| Sheet 選單 | 改稱「🔑 顯示 API KEY（交 ADMIN）」（handler 沿用 `menuShowLinkCredentials`）；沒有自動驗證或手動設定 BACKEND／旅團編號的選單 |
| 舊 URL 快取及既有屬性 | 不再讀取來顯示；不擅自刪改既有 Script Properties |
| 前端及文件 | 中英部署說明、下載參數（`?gs=v9.2`）、GS 版本／初始化標記同步更新，不新增貼網址到 GS 的設定步驟 |
| Workspace URL 格式 | 伺服器 Registry 及接入申請轉發只把 `/a/<網域>/macros/s/<部署 ID>/exec` 轉成相同部署 ID 的公開路徑；不代表修正錯 ID 或改變 Google 權限，亦不接受 HTTP、query、fragment、帳密或自訂連接埠 |

正式部署網址仍由 Google 部署視窗提供；用戶在原有 ADMIN FORM 自行填寫編號、名稱、URL 和 API Key。原有 API Key、業務資料、深資綱要與權限、登入／簽名協定全部不變。非 JSON 回應不能直接證明是錯誤／舊部署，排障時不可如此斷言。

## 5. 安全邊界核實

系統介紹會說明「私人 Sheet 不等於所有資料 API 自動安全」。已核實深資現況：部分舊式資料讀取入口的登入／權限驗證仍待補強，本次沒有修復，亦不可把介紹圖當成獨立安全認證或宣稱所有讀取已受登入保護。帳號密碼登入本身每次均核實帳號及密碼，用戶自行設定系統密碼，首次登入須更改臨時密碼；API Key 是系統連接鑰匙，不是個人登入驗證。

## 6. 回歸驗收

`tests/credential-display.test.mjs` 覆蓋：

- Google 可能回傳三個不同 URL、同時存在舊 URL 快取時，各顯示位置都不顯示／回傳任何部署 URL。
- 初始化實際彈窗及執行回傳值，確實提供原有 API Key 及深資原有首次登入提示，沒有 `scriptUrl`／`backend`。
- 顯示功能不讀取 Google service URL、不探測候選網址、不要求用戶貼網址；Google URL 讀取及網路同時失敗亦照常運作。
- 新安裝沒有旅團編號亦可直接生成 API Key；初始化及選單無任何編號／網址設定提示，重跑保留同一 Key。
- 普通 HTTP 請求不改寫 URL 快取；不存在自報 URL 核實入口。
- 新選單標示 API KEY，沒有自動驗證或手動 BACKEND／編號設定步驟。
- 重複初始化／查看保留 API Key、已有業務紀錄、旅團設定及舊快取原值。
- Workspace 格式只轉相同部署 ID 的公開路徑，且正規化不放寬白名單。

`tests/system-intro.test.mjs` 覆蓋系統介紹分頁雙向切換、中英鍵完整及真實語言切換渲染、圖片及 `Code.gs` 下載不被部署忽略。

測試使用本地假資料，沒有讀取用戶的線上資料或修改 Google 部署。**本文件及 repository 修改不代表任何旅團的 Google Apps Script 已更新**；各旅團仍須自行更新 `Code.gs`、執行一次 `initializeSheets()` 並以「新版本」重新部署，部署後再以實際 Sheet 介面確認顯示行為。
